# CLI and Results Contract

`python -m shape_classifier train [existing options] [--cpu-threads N]`: N is a positive integer no greater than process-available CPUs. Omission retains feature 004's all-available default. Invalid input fails nonzero, naming requested and available counts for an excessive request, before data loading or checkpoint/results/recovery writes. Startup reports the configured CPU computation pool count and request/default status. Evaluation and prediction retain existing behavior.

For Docker, the documented host launcher queries the selected running Colima profile and matches its reported Docker socket to the effective Docker endpoint before passing an observation to its container invocation. The handoff is a JSON object in `SHAPE_COLIMA_OBSERVATION`: `version` is integer 1, `cpus` is a positive integer, `profile` is a nonempty string, and `docker_endpoint` is a nonempty normalized Unix-socket URI. The launcher emits it only after matching the selected running profile’s socket to the effective Docker endpoint; it removes any inherited value and passes no object if the query or match fails. The container accepts only this schema and otherwise records `"unknown"` and warns. This environment value is an unauthenticated launcher assertion: it can be forged and cannot independently prove endpoint identity inside the container. The VM and Docker endpoint must remain unchanged during the run. A known VM count differing from an explicit thread request produces a warning naming both; training continues if the request is within process availability. A known matching count produces no mismatch warning. No application command modifies the VM. Direct Docker invocation remains supported and can report unknown.

New entries add `requested_cpu_threads` as an integer or null. Docker entries also add `docker_cpu_provenance` as `launcher` for a valid launcher observation or `unknown` for an unknown allocation; legacy entries lacking it are `legacy-unverified` and retain their recorded count. Legacy entries without `requested_cpu_threads` remain valid and are interpreted as default; see [data model](../data-model.md). The summary command retains its existing interface and groups by actual threads and Docker VM allocation and provenance in addition to existing keys, so legacy-unverified and launcher observations never share a row. It displays counts and default/explicit/mixed request provenance, VM allocation and allocation provenance, and whole-GPU labeling for MPS. It retains paired accuracies, missing configurations and measured values without scaling. Summary does not mutate results. Existing sequential access and transactional recovery contracts remain in force.
